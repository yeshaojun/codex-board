# Session Note: Loctek Specboard 的本地优先产品方向

## 决策背景

用户希望通过看板统一管理多个项目的 `.changes` 与 OpenSpec，也希望能在讨论后找回方案、计划、关键架构选择，并从零散记录生成适合分享与复盘的完整文档。

## 用户决策

- 同意创建独立的 `loctek-specboard`，以 `loctek-ai-cowork` 为首个真实扫描项目。
- 讨论、方案和计划必须成为看板内容，不能只存在 AI 会话或散落 docs。
- 需要生成由浅入深的一份项目文档：非技术人员能理解价值与当前情况，技术人员能追溯问题、方案、验证和架构边界。

## 实现方式

- Markdown/Git 继续是唯一事实源；Specboard 只创建可审计的 discussion/plan 源文件和可重建视图。
- 新增 `.changes/discussions/`、`.changes/plans/` 作为长期可检索的讨论和计划落点，与 session note、issue、work/test/merge report 互链。
- 叙事文档在每一项保留源路径，并把没有报告/测试/合并证据的内容标为待补证。

## 替代方案（已排除）

- 直接 fork Taskboard 的 Codex UI 注入实现：第一版会绑死桌面内部实现，且不解决项目知识、Git 审计与文档叙事。
- 把 AI 原始对话全文存入看板：包含噪声、潜在敏感信息且难以维护，改为提炼结论与关联。
- 创建单独数据库作为任务真相：会与 Markdown/Git 产生双写漂移。

## 已知限制

- 不能可靠回收历史所有 AI 对话；需要后续通过 capture 主动沉淀。
- 当前 Marketplace 目录权限阻断了插件登记，代码与 Skill 先在独立仓验证。

## 影响面

- 独立 Specboard 项目、未来多项目配置、Loctek skills 使用方式；不触碰现有业务系统边界。

## 回滚计划

- 停止本地 server 并移除独立插件即可；用户创建的 Markdown 记录可由 Git 还原。

## 控制台信息架构补充

用户确认对日常项目管理最有价值的信息是任务责任与时间、执行事实、归档阻塞和下一步，而非纯 Kanban 排列。产品界面据此采用：

- **概览**：任务状态、建议优先处理项、显式阻塞和归档前待补证；
- **任务**：可筛选的密集列表，固定展示创建时间、创建者、最近更新、风险和归档前检查；
- **方案与计划**：discussion、plan、OpenSpec change；
- **架构**：仅 ADR，避免将临时会话记录误标为架构基线；
- **决策**：session note 与 discussion，保留推理和取舍但不替代 ADR。

实现必须继续以 Markdown/Git 为事实源；看板生成的“推荐下一步”只用于辅助判断，不是自动工作流，也不代表任务完成或可归档。

## 本地可用性与 Codex 接入补充

用户希望看板页面稳定可访问，并问如何让项目在 Codex 中出现。决定将两件事分开：

- localhost 看板作为交互界面，由本机登录态下的 launchd 守护，仅绑定 loopback；
- Codex 通过仓库自带的显式 local marketplace 安装插件，获得 Skill 和推荐提示词；它不是把网页嵌入 Codex，也不依赖 root-owned 的默认个人 marketplace。

该分离确保 Codex 对话工作流和项目看板共用同一 Markdown/Git 事实源，同时分别使用最适合的交互入口。

## 跨项目与侧栏入口决策

### 决策背景

用户澄清看板不应只绑定 `loctek-ai-cowork`：日常会在多个 Codex 项目之间切换，也会先做无仓库的方案讨论。单独 URL 即使可访问，也不能解决“从 Codex 中快速进入全局工作台”的问题。

### 用户决策

- 看板以所有登记项目为范围，第一屏默认给出组合概览；单项目只是过滤条件。
- 接受参照 Dashi 的独立 Codex 窗口 + loopback CDP/DOM 注入方式，在左侧栏加入直接入口。
- 接受该方案是非官方兼容层、可能随 Codex 更新而需要维护的权衡。

### 实现方式

- `projects.json` 仅保存本机项目 label/path；`.changes`、OpenSpec 与 Git 仍是任务和知识事实源。
- 专用窗口使用独立 profile，调试端口固定为 loopback `127.0.0.1:9232`；正常 Codex 窗口不会被附加或注入。
- 注入器只克隆原生侧栏按钮的视觉结构，嵌入 `http://127.0.0.1:47932/?host=codex`，不桥接会话、Composer、用户身份或凭据。
- 启动器持续 watch renderer replacement，并且不修改 `ChatGPT.app`、`app.asar` 或用户原始项目文件。

### 替代方案（已排除）

- 仅用 Marketplace plugin/Skill 加浏览器 URL：官方 manifest 不能添加可嵌入的侧栏页面，入口仍然分散。
- 直接注入用户正在使用的普通 Codex 窗口：影响面太大，且会把非官方行为混入日常工作环境。
- 另建中心化任务数据库：会破坏 Markdown/Git source-first 原则。

### 已知限制与回滚

- 独立 profile 初次启动如未继承 app 登录态，可能需要在该窗口完成正常登录；本工具不复制浏览器 cookie 或凭据。
- 退出 `npm run codex` 后，已经打开的页面可能继续显示，但 renderer 重载不再自动重挂入口。
- 回滚方式是关闭专用窗口、停止启动器并删除 `inject/` / `scripts/codex-*`；不影响普通 Codex 与被扫描项目。

## 嵌入页刷新一致性补充

### 决策背景

用户要求 Codex 左栏入口展示全局项目组合。实测发现，当侧车同步 Codex 项目后，iframe 有时保留旧扫描结果；服务端数据是正确的，但页面没有可靠地等到新组合加载完成。

### 用户决策

- 侧栏入口必须以完整的已登记项目组合为准，不能以旧缓存或“正在读取”状态作为成功。
- 无法扫描的项目应展示 warning，但不能阻塞其余项目的组合视图。

### 实现方式

- 侧车从 `/api/projects` 读取当前项目数，向受控 iframe 调用一次显式加载，完成后验证项目切换 pill 数相等才标记为 loaded。
- 移除嵌入文档中的外部脚本标签，避免自动加载与侧车加载竞争；脚本改在 IIFE 中运行，避免 CDP document replacement 遗留全局 lexical binding。
- 验证内容限于页面结构、标题、项目名称和错误提示，不读取 Codex 对话、cookie、composer 或凭据。

### 替代方案（已排除）

- 仅检查 `app.portfolio` 是否非空：它不能区分旧数据与本次扫描数据。
- 让 iframe 每次自行自动加载：存在与项目同步竞争的时序，无法保证页面显示最新组合。

### 已知限制

- 每个慢项目仍受 8 秒扫描上限约束，跨项目首次刷新可能需要约 16 秒；这是为了避免单一项目卡住看板。
- Codex UI 或 CDP 行为变化仍可能要求维护侧栏 selector/嵌入策略。

## 项目级经营视图补充

### 决策背景

用户确认日常入口应先回答“哪个项目需要关注”，而不是把所有项目的任务混排；同时，项目切换应从不断增长的 pill 列表改为简洁的下拉选择。

### 用户决策

- 项目选择使用一个下拉框，支持全部项目和单项目进入。
- 默认概览必须按项目展示统计；单项目才展示具体任务判断与状态分布。
- 页面风格需要更有层级，适合项目经营台账，而不是普通任务列表。

### 实现方式

- 全部项目概览渲染项目摘要行：活跃、阻塞、待补证、高风险和知识记录，并给出一项推荐关注任务；点击行进入该项目。
- 单项目沿用已有任务状态条、优先处理、阻塞和归档待补证面板，避免丢失具体执行判断。
- 头部改为深绿控制台，项目选择器与摘要行突出层级及危险/待补证状态。
- 对 Codex iframe，由侧车从 loopback 预取项目组合并注入，再由前端消费；避免 opaque `about:blank` iframe 对 fetch 的兼容问题。侧车 hash 覆盖注入脚本和 `public/` 资源，UI 更新会强制重建嵌入页。

### 替代方案（已排除）

- 保留 pill 并加滚动：项目数量扩大后仍难快速定位，且会占据横向空间。
- 在组合首页继续按任务展示三列面板：无法支持项目之间的整体优先级比较。
- 引入图表库：当前任务统计是直接计数，额外依赖与动画会削弱工作判断的密度。

### 已知限制

- 当前统计是当前扫描快照，不是历史趋势；项目健康度不会被伪装成趋势或完成率。
- 无法扫描项目仍仅显示原因，不能提供统计；其余项目照常可用。
