# Work Report: 实现仓库原生协作任务闭环

## Issue

- File: `.changes/issues/issue-003-仓库原生协作任务闭环.md`
- ID: ISSUE-003

## Understanding

用户要的不是把 Specboard 变成第三方工单系统，而是把 Codex + Loctek Skills 的工作过程留在项目 Markdown/Git 中：创建者默认承担任务，转交、状态和讨论可以直接在看板完成且可追溯。

## Decision Log

### 用户关键决策

- 不接 GitHub/GitLab/Jira，也不引入额外数据库。
- 任务、评论、负责人和过程都写回项目中的 Markdown，随 Git 协作。
- Loctek Skills 保持为创建、实现、测试、提交、合并和归档的执行入口。
- 新建 Issue 的创建者默认就是负责人，负责人之后必须能修改。

### 实现思路

- 增加小而明确的 Issue frontmatter 协议和追加式协作动态。
- API 只在已登记项目中查找已扫描 Issue 文件，避免客户端提供任意路径。
- `created_by` / `assignee` 缺失时用 Git 创建者回退，兼容旧 Issue 和当前只读的全局 Issue 生成器。
- 根据状态和证据只提示下一步应使用的 Skill；不由网页后台执行 Skill。

### 放弃方案

- 不建立 SQLite/PostgreSQL 任务表：会造成 Markdown 与数据库双事实源。
- 不依赖 GitHub/Jira connector：超出本地项目协作目标。
- 不从浏览器读取或伪造 Codex 对话身份：当前仅以项目 Git 用户标注本机写入者。

### 合并时必须保留

- loopback-only 监听和写入范围约束。
- 协作历史追加而非覆盖。
- 任务状态不等于实现或测试已完成，仍需要 Loctek 证据链。

## Investigation

- 已读取 Specboard 扫描、服务、前端、测试与本项目 Loctek 记录。
- 已确认当前全局 `loctek-issue` 安装目录不可由当前用户修改；因此实现需要兼容旧模板的 Git 回退。

## Implementation

已完成核心实现：

- `src/lib.mjs` 读取 Issue 的 `created_by`、`assignee`、`reviewers` 与追加式协作动态；旧任务以 Git 创建者回退。
- 新增受控 `updateIssueRecord()`，只定位活动 `.changes/issues/` 中匹配 ID 的文件，限制可写字段和状态，并以 Git 用户追加审计动态。
- `src/server.mjs` 新增项目 ID + Issue ID 的 PATCH 路由；服务继续只绑定 loopback。
- 详情页增加负责人、状态、评论编辑，动态时间线和只提供提示的 Loctek Skill 接力卡。
- 补充协作协议与知识资产文档；全局 `loctek-issue` 安装目录的默认字段改造仍需要系统所有者的安装权限。
